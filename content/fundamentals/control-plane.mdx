## Ein gewünschter Zustand, viele kleine Schritte

Mit einem Deployment beschreibst du einen gewünschten Zustand, zum Beispiel zwei Instanzen einer Anwendung. Kubernetes arbeitet kontinuierlich daran, den tatsächlichen Zustand anzugleichen. Diesen Regelkreis nennen wir **Reconciliation**.

### Die Komponenten der Control Plane

- **kube-apiserver** prüft und verarbeitet API-Anfragen. Die anderen Komponenten kommunizieren über die API.
- **etcd** speichert den Clusterzustand. Es ist keine Anwendungsdatenbank für deine Workloads.
- **kube-controller-manager** führt Regelkreise aus. Deployment- und ReplicaSet-Controller erzeugen die benötigten Ressourcen.
- **kube-scheduler** weist noch nicht eingeplanten Pods geeignete Nodes zu.
- **kubelet** auf dem gewählten Node lässt die Runtime die Container starten und meldet den Status zurück.

### Warum startet der API Server keinen Container?

Die Control Plane koordiniert den gewünschten Zustand. Die Ausführung liegt auf den Nodes. Diese Trennung ermöglicht es, ausgefallene Instanzen auf anderen geeigneten Nodes neu zu erstellen.

### Wenn ein Pod Pending bleibt

Prüfe im echten Cluster zuerst `kubectl describe pod NAME`. Unzureichende Ressourcen, nicht passende Node-Selektoren, Taints oder ein noch nicht gebundenes Volume können Scheduling verhindern. Der Scheduler schafft selbst keine zusätzliche Rechenleistung.

## Was nach `kubectl apply` tatsächlich passiert

Ein erfolgreiches `apply` bedeutet zunächst, dass die API den gewünschten Zustand angenommen hat. Es bedeutet nicht, dass bereits ein Container läuft. Die folgenden Schritte passieren verteilt und nicht als eine einzige Transaktion:

1. `kubectl` sendet eine API-Anfrage. Der API Server prüft Authentifizierung, Autorisierung, Schema und Admission-Regeln. Mutierende Admission kann Felder ergänzen; validierende Admission kann die Anfrage ablehnen.
2. Der akzeptierte Deployment-Zustand wird über den API Server in etcd persistiert. Die Antwort an den Client ist keine Bereitschaftsgarantie.
3. Der Deployment-Controller vergleicht Soll und Ist und erstellt oder aktualisiert ein ReplicaSet. Der ReplicaSet-Controller erzeugt die fehlenden Pod-Objekte.
4. Der Scheduler beobachtet Pods ohne Node-Zuweisung, filtert geeignete Nodes, bewertet Kandidaten und schreibt eine Bindung über die API.
5. kubelet sieht die Zuweisung, koordiniert Netzwerk und Volumes und lässt die Runtime Container starten. Statusmeldungen gelangen zurück zur API. Erst erfolgreiche Readiness-Prüfungen machen einen Pod für regulären Service-Verkehr bereit.

Controller erhalten Änderungen über API-Watches und wiederholen ihre Regelkreise bei Bedarf. Sie müssen mit veralteten Beobachtungen, Konflikten und Wiederholungen umgehen können. Eine Watch ist kein direkter Aufruf vom API Server an den Controller, „jetzt genau diesen Container zu starten“.

## Sollzustand, Status und Selbstheilung

`spec.replicas: 3` ist dein Wunsch. `status.readyReplicas: 1` beschreibt eine Beobachtung. Wenn eine Instanz fehlt, erzeugt der ReplicaSet-Controller Ersatz; der Scheduler und kubelet übernehmen danach ihre jeweiligen Schritte. Kubernetes repariert dabei nicht automatisch einen Fehler in deinem Anwendungscode.

Ein gelöschter einzelner Pod eines Deployments erscheint deshalb meist als neue Instanz wieder. Ein auf null skaliertes Deployment bleibt dagegen ohne Pods: Null ist dann der gewünschte Zustand. Diese Unterscheidung übst du im Operations-Szenario **Verschwundene Workloads**.

## Fehler entlang der Zuständigkeitsgrenzen eingrenzen

| Beobachtung | Zuerst prüfen | Zuständigkeit |
| --- | --- | --- |
| API liefert Forbidden | Benutzer, ServiceAccount, RBAC | API-Autorisierung |
| Deployment existiert, Pods fehlen | ReplicaSets, Events, replicas | Controller und Admission |
| Pod bleibt Pending | Events, Requests, Taints, Volumes | Scheduling oder Vorbereitung |
| Pod hat Node, Container startet nicht | Pod-Events, Runtime, Image-Zugriff | kubelet und Runtime |
| Pod läuft, Service liefert keine Antwort | Readiness, Selektor, EndpointSlices, Netzwerk | Workload und Datenpfad |

kubectl describe deployment hello-kubelab

## etcd und Ausfälle

etcd benötigt für Änderungen eine Mehrheit seiner Mitglieder. Drei etcd-Mitglieder können einen Ausfall tolerieren; zwei Ausfälle verlieren das Quorum. Drei Worker mit nur einer Control Plane machen die Control Plane nicht hochverfügbar. Bestehende Container können bei einer vorübergehend unerreichbaren API weiterlaufen, neue Platzierungen und Änderungen sind jedoch eingeschränkt.
