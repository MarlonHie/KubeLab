## Cilium verbindet und kontrolliert Pod-Verkehr

Cilium ist in unserem kubeadm-Lab das CNI-Plugin. Es verwendet unter anderem eBPF für Teile des Datenpfads und unterstützt Netzwerkrichtlinien. Der Cilium-Agent läuft auf den Nodes; der Operator übernimmt clusterweite Aufgaben. **Hubble** ergänzt die Beobachtung von Netzwerkflüssen und muss dafür gesondert aktiviert werden.

Unser Lab bleibt bei Cilium 1.19.0 mit VXLAN und laufendem kube-proxy. Die optionale vollständige kube-proxy-Ersetzung ist eine andere Konfiguration und kein notwendiger Schritt für dieses Modul.

### Voraussetzungen und Ausführungsort

**Echte Ausführung im externen VM-Terminal.** Verwende den isolierten Drei-VM-Cluster aus dem Build Lab. Alle Nodes und Cilium-Pods müssen bereit sein. Diese Übung wird nicht vom Browserterminal ausgeführt. Nutze ausschließlich den dedizierten Namespace `kubelab-net`.

```bash
kubectl -n kube-system get pods -l k8s-app=cilium -o wide
kubectl -n kube-system rollout status daemonset/cilium
kubectl create namespace kubelab-net
kubectl -n kubelab-net create deployment web --image=nginx:1.28
kubectl -n kubelab-net expose deployment web --port=80
kubectl -n kubelab-net rollout status deployment/web
kubectl -n kubelab-net run client --image=busybox:1.37 --restart=Never --labels=role=client --command -- sleep 3600
kubectl -n kubelab-net wait --for=condition=Ready pod/client --timeout=120s
kubectl -n kubelab-net exec client -- wget -T 5 -qO- http://web
```

Erwartung: Die letzte Zeile liefert die nginx-Seite. Falls nicht, stoppe vor der Policy-Übung und prüfe DNS, Service-Endpunkte und Cilium-Status.

### Einen gezielten Netzwerkfehler erzeugen

Speichere dieses Manifest als `deny-web.yaml` in deiner Lab-VM und führe dort `kubectl apply -f deny-web.yaml` aus. Es isoliert ausschließlich eingehenden Verkehr der ausgewählten Web-Pods im Übungsnamespace. DNS-Egress des Clients wird davon nicht gesperrt.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-web-ingress
  namespace: kubelab-net
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
    - Ingress
  ingress: []
```

Wiederhole den HTTP-Aufruf. Nach der Policy-Übernahme sollte er mit einem Timeout scheitern. Eine weiterhin erfolgreiche Anfrage kann auf noch nicht übernommene Regeln, nicht passende Labels oder fehlende Policy-Durchsetzung hinweisen.

### Die Verbindung gezielt erlauben

Erstelle eine zweite Policy `allow-client` im selben Namespace, mit demselben Zielselektor `app: web`. Ihre `ingress`-Regel soll nur Quellen mit dem Pod-Label `role: client` und TCP-Zielport 80 zulassen. Kubernetes-NetworkPolicies sind additiv: Die passende Allow-Policy öffnet diesen Verkehr trotz der weiterhin vorhandenen leeren Ingress-Policy.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-client
  namespace: kubelab-net
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              role: client
      ports:
        - protocol: TCP
          port: 80
```

### Prüfen, erklären, zurücksetzen

Die HTTP-Anfrage soll wieder erfolgreich sein. Entferne testweise das Client-Label mit `kubectl -n kubelab-net label pod client role-` und prüfe, dass der Zugriff nach der Policy-Übernahme wieder scheitert. Erkläre, warum die Quelle und nicht nur das Ziel relevant ist.

Setze ausschließlich diese Übung zurück:

```bash
kubectl delete namespace kubelab-net
```

Die automatische KubeLab-Prüfung dieses Moduls ist ein Wissenscheck. Ein bestandenes Quiz bestätigt nicht, dass die Netzwerkübung auf deinen VMs funktioniert hat.
